# RevPilot AI — AI vs. Deterministic Decisions

Every calculation in RevPilot is either **deterministic** (plain code —
SQL, pandas, rule-based logic) or **AI** (LLM-generated). This document
records which is which, and why, so the boundary is never ambiguous.

| Capability | Approach | Why |
|---|---|---|
| Revenue metrics (total revenue, AOV, conversion, repeat rate) | Deterministic | Financial figures must be exact and auditable, not generated |
| RFM segmentation | Deterministic (rank-percentile + rule-based) | Reproducible, explainable, no training required |
| Product affinity (support/confidence/lift) | Deterministic (market-basket analysis) | Classic statistics over real transactions — an LLM would guess, not compute |
| Opportunity scoring | Deterministic (weighted formula, min-max normalized) | Must be traceable to the inputs that produced it |
| Policy checks (discount caps, budget caps) | Deterministic | Financial safety cannot depend on model behavior |
| Permission checks | Deterministic | Same reason — must be a hard gate, not a suggestion |
| Payment verification / webhook processing | Deterministic | Correctness-critical, signature-verified, idempotent |
| Revenue attribution | Deterministic | Must be defensible, not inferred |
| Intent understanding (agent chat, buyer chat) | AI | Natural language has no deterministic parser |
| Opportunity/campaign explanation in prose | AI | Turning structured evidence into a readable narrative |
| Buyer conversation (AI Buyer) | AI | Understanding "something under ₹5,000 for gaming" requires language understanding |
| Candidate re-ranking commentary | AI | Explaining *why* a ranked list looks the way it does |

## The rule this table encodes

**If a number appears anywhere in the product — a price, a discount, a
revenue figure, a conversion rate, an inventory count — it was computed by
code, not generated by a model.** The LLM's job is to read those numbers,
reason about which tool to call next, and explain results in plain
language. It never invents a number and it never has final authority over
a financial action (see `docs/agent-tools-permissions-policy.md` for the
enforcement mechanism — the Action Pipeline).

## Estimated vs. attributed

Two different kinds of "revenue" appear in the product and must never be
conflated:

- **Attributed revenue** — a payment that is demonstrably tied to a
  specific order/campaign, recorded after the fact from real payment
  events.
- **Estimated revenue** — a projection made *before* an action has run
  (e.g. an opportunity's `estimated_revenue_amount`, or a simulation's
  `expected_incremental_revenue`). Every estimate carries its assumption
  explicitly in `evidence_json` (e.g. "recovery rate assumed at 12%,
  industry-typical benchmark, not yet measured for this merchant") so the
  UI can label it `ESTIMATED` rather than implying certainty.

This distinction is enforced structurally: `revenue_attributions.attribution_type`
is a stored enum (`attributed` | `estimated_incremental`), and every
opportunity candidate in `app/opportunities/scoring.py` that relies on an
unproven assumption documents that assumption inline rather than
presenting a bare number.
